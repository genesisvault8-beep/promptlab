Prompt Engineering for Code Generation

Getting reliable output instead of confident-sounding bugs

AI-generated code fails in a specific, predictable way: it looks correct, compiles or runs at first glance, and then breaks on an edge case or calls a function that doesn't exist. Most of that isn't a model limitation — it's missing context in the prompt. Here's what actually moves the needle.

State the environment explicitly

Language version, framework version, and runtime matter more for code than for almost any other prompt type. "Write a Python script" versus "write a Python 3.11 script using only the standard library, no external dependencies" produce very different reliability.

Write a function in Python 3.11 that reads a CSV file and returns rows as dictionaries. Use only the standard library (no pandas). Include type hints and handle the case where the file doesn't exist by raising a clear error, not a bare exception.

Show, don't just describe, your existing code style

If you're adding to an existing codebase, paste a short snippet of your actual code as an example before asking for new code in the same style. Models pattern-match far better from an example than from a description like "use my usual style."

Ask for the failure modes, not just the happy path

By default, models tend to generate code for the case where everything goes right. Explicitly ask what happens on bad input, empty results, network failure, or concurrent access if those matter for your use case — otherwise you'll often get code that works in the demo and breaks in production.

Break large tasks into steps

Asking for an entire feature in one prompt tends to produce code that's individually reasonable but doesn't fit together well — inconsistent naming, mismatched assumptions between functions. Better results usually come from asking for one function or module at a time, reviewing it, then asking for the next piece with the previous one as context.

Ask it to flag uncertainty

A useful pattern: explicitly instruct the model to say "I'm not certain this API exists / this is the current syntax" rather than presenting a guess with full confidence. This won't eliminate hallucinated methods entirely, but it surfaces the riskiest parts of the output so you know what to verify first.

Before writing the code, list any libraries or APIs you're not fully certain about. Then write the implementation. If you're guessing at a method name or signature, say so in a comment.

Specify inputs, outputs and an example

The clearest way to describe a function is to say what goes in, what comes out, and show one concrete case. It removes a whole class of misunderstandings about edge cases and return types:

Write a JavaScript function parseDuration(str) that converts strings like "1h 30m" or "45s" into total seconds. Input: a string with any combination of h, m and s parts. Output: an integer number of seconds. Return null for invalid input. Example: parseDuration("1h 30m") returns 5400. No external libraries.

Ask for tests alongside the code

Requesting tests does two things. It forces the model to think through the cases, and it gives you something to run immediately. Ask for a handful of tests that include at least one edge case and one failure case, in the framework you actually use:

Now write 5 unit tests for this function using Jest. Include an empty string, a malformed string, and a very large value. Tell me if any test depends on an assumption I should confirm.

Debugging prompts that actually work

"This doesn't work, fix it" gives the model almost nothing. A good debugging prompt contains four things: what you expected, what actually happened, the exact error message, and the smallest piece of code that reproduces the problem.

Expected: the function returns a sorted list of unique emails. Actual: it returns duplicates when emails differ only by letter case. Error output: none, the result is just wrong. Code: [paste only the relevant function] Explain the cause first, then show the minimal fix. Don't refactor anything else.

Use the model as a reviewer

Models are often better at critiquing code than writing it perfectly on the first pass. After generating something, start a fresh prompt that reviews it with a specific lens, such as security, performance or readability:

You are a security-minded reviewer. Review the code below for injection risks, missing input validation, unsafe use of user input in file paths or queries, and secrets in code. List each issue with severity and a one-line fix. If you find nothing, say so.

Setting this up as a reusable instruction is a good use of a system prompt. We explain the difference in System Prompts vs User Prompts.

Verify before you trust it

  • Run it. Plausible-looking code that has never been executed is not a result.
  • Check unfamiliar APIs against the official documentation, especially method names and argument order.
  • Read every line you don't understand. If you can't explain it, ask the model to explain it before you ship it.
  • Test the edges: empty input, very large input, wrong types and failure of any network or file call.

Common mistakes with code prompts

  • Leaving out versions. Library behavior changes between releases, and the model may default to an older or newer API than you use.
  • Asking for everything at once. Build in steps and review each one.
  • Pasting secrets. Never include real API keys, tokens or passwords in a prompt. Replace them with placeholders.
  • Accepting a rewrite when you asked for a fix. Say "change only what is needed" so the diff stays small and reviewable.

Frequently asked questions

Which AI model is best for code?

It depends on the language and the task, and the answer changes as models update. Claude and GPT-4o are both commonly used for code. Rather than trusting a general ranking, run your own prompt on both and compare, as we describe in our model comparison guide.

Should I paste my whole codebase into the prompt?

Usually not. Paste only the files and functions that matter for the task, plus a short description of how they connect. Too much unrelated code buries the part the model should focus on, and it raises cost without improving the answer.

How do I stop the model from inventing functions that don't exist?

You can't eliminate it, but you can reduce it. State the exact library and version, paste the relevant documentation or type signatures when you have them, and ask the model to flag anything it is unsure about. Then run the code and check unfamiliar calls against the official docs.

Is AI-generated code safe to use in production?

Treat it like code from a new teammate: review it, test it and understand it before you merge it. Pay extra attention to input validation, authentication, error handling and anything that touches secrets or user data.
